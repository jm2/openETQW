### Found this session
- **An optimized game module could not start a map on macOS** (2026-09-30, the macOS validation pass). `sdPropertyValue() {}` (game `src/idlib/Properties.h:70`) left `value` uninitialized, and `operator=` compares it before assigning (`PropertiesImpl.h:455`). For the `int` a `handle` global property creates (`PlayerProperties.cpp:1739-1743`), Apple Clang 21 at `-O2` treats that read as undefined behaviour and removed the branch, so `sdGlobalPropertiesNameSpace::Init` rejected `Invalid Type 'handle'`, `game->Init` failed on the retail data, and the map load crashed (SIGSEGV in `idCompiler::ParseSysObjectCall`). Debug builds, which every macOS retail row used, were unaffected; releases build `debugoptimized` (`manual-release.yml`). Fixed by value-initializing (game `fix/property-value-init`). The assetless smoke's stub decls now carry a `guiGlobals` stringMap with a `handle` entry: with an optimized build it fails on the old module and passes on the fixed one.
- **The macOS app could not be packaged.** The renderer reaches Vulkan only through `SDL_Vulkan_LoadLibrary` (`VK_NO_PROTOTYPES`), so Meson's default `b_asneeded` (`-dead_strip_dylibs` on macOS) dropped the Vulkan loader from the client, and `package_release.py` refuses a client that does not link it. The client now links it on macOS (`override_options`, engine `fix/macos-release-build`); the app then loads the bundled loader, which finds the bundled MoltenVK through `Contents/Resources/vulkan/icd.d`.

- **canyon hung the GPU: misaligned frame-temp vertices (fixed).** Not a driver bug: the kernel log names this process as the one whose job timed out (`ring gfx_0.0.0 timeout … Process openETQW-client`; one run escalated to a MODE1 reset with VRAM lost). A `RADV_DEBUG=hang` dump put the hang in the strogg hog's (`_MD5_Snapshot_`) unshadowed interaction draw, whose frame-temp vertex block sat at offset 888770 (2 mod 4): index blocks (three 2-byte indexes per triangle) shared the arena unaligned, and Vulkan requires 4-byte-aligned float attributes. Frame-temp blocks are now 16-byte aligned.
- **Under Vulkan the vertex cache never ended a frame (fixed; macOS too).** `vertexCache.EndFrame()` ran only when `openGLRunning`, false under Vulkan since ed2de0d. The 16 MB temp arena never rewound (every temp allocation after it filled became a new `VkDeviceMemory`) and deferred frees never ran, so GPU memory grew for as long as the game ran; each stuff-snapshot rebuild leaked ~70 buffers. On RADV the growing allocation cost stalled frames 45–90 ms while turning.
- **The frame-poses failures were not the host.** The validation layer, then on by default (`r_vkValidation 1`) wherever it is installed, cut the uncapped rate from ~370 to 56 fps (the default is 0 since 2026-09-27; the correctness tests turn it on); the leak above added the stalls; and the test walked the observer into the peer (both spawn on one line on valley, turns are 180 degrees) and into a wall. `frame-poses` now runs without the layer and puts the players in separate lanes. The stuff snapshot rebuild (every 10 degrees of turning) cost 12–15 ms, mostly per-surface `VkDeviceMemory` allocations and a scan of every instance of the map; snapshots now stream through the frame arena and skip cells beyond the fade distance.
- **Static vertex-cache buffers each owned a `VkDeviceMemory` (fixed on the Windows branch, PR #23).** About 3,700 were live on valley (4,975 allocations in all), against the 4096 `maxMemoryAllocationCount` NVIDIA and Intel Windows drivers report (the AMD hosts report 4294967295, so no host here could show it). They are now bound into shared 32 MiB blocks: valley peaks at 1,294 allocations; under the Khronos profiles layer simulating the 4096 limit the old build reports `VUID-vkAllocateMemory-maxMemoryAllocationCount-04101` and the new one nothing. `vulkan-shadows` and `campaign-client-maps` now fail at 4096.
